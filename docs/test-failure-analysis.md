# 测试失败分析智能体（页面集成）

入口：`/production/defect-search/test-failures` → 报告列表的异常摘要下方 → **失败分析与处理建议**。报告详情中也可查看同一份结果。列表每行对应一个独立文件夹，不关联同一移液器在其他文件夹中的报告。

本次将 `opentrons/hardware-testing/analysis/pipette_qc_agent` 的证据解析、分析规则和模型校验核心复制到本工程，并接入现有测试失败页面。仅修改本地工程；没有部署、启动服务器服务或恢复原先停用的独立智能体。

## 如何使用

1. 按 [测试失败数据](test-failure-data.md) 配置报告归档目录并索引报告。
2. 在报告行的分析卡片中选择证据包并点击“生成分析”。有搜索或筛选条件时默认选择同时命中条件的证据包；无条件时选择当前文件夹内的主报告，只有参考快照时先显示快照。仅可切换本文件夹中的主报告和各规格参考快照，卡片标出对应测试时间与异常类型，不借用其他文件夹中同 SN 的主报告或分析结果。
3. 页面显示后台分析状态，完成后默认展示前两项简版建议，包含分析结论、优先检查、处理方向及复测要求。点击“展开完整建议”查看全部问题、完整步骤、证据和分析限制；“查看依据”直接打开当前所选报告的详情。上述操作保留页面上的返修草稿。
4. 品质人员核对现场情况后，在原有返修确认入口填写确认内容。生成分析不会自动保存人工确认，也不会将测试判定改为通过。

分析按当前报告触发，不会在打开页面、定时扫描或后端启动时自动调用模型。只读账号可查看已有结果；可编辑账号可以发起分析。普通生成请求复用相同输入的完成结果；需要重新执行时，点击“重新分析”。该操作按当前后端配置再次执行规则或模型分析，报告证据、返修确认和其他文件夹不受影响。

列表和详情按报告 ID、失败 revision 与独立 evidence_version 共享分析状态、请求和轮询；附件版本变化会切换订阅，旧请求的迟到响应不覆盖新状态；同时打开同一报告不会重复提交任务。只有分析中的报告持续轮询，当前页面状态查询最多三个并发。行内分析进入视口附近后才加载状态，普通列表刷新不会重新查询所有已加载卡片，也不清空未变化的详情、附件和展开状态。手动状态刷新优先于尚未开始的后台查询；重复点击或在列表与详情同时刷新仍复用同一个请求。

“刷新状态”只查询已有分析状态，按钮及提示会显示等待或刷新过程，成功后显示检查时间；当前结果没有变化时，原生成时间也不会变化。请求失败时显示错误，不显示成功提示；切换报告后不显示上一份报告的刷新反馈。打开页面、刷新列表或扫描完成后的自动查询不会冒充手动刷新成功。证据变化时隐藏不匹配的旧结果，并提示刷新报告或重新分析。

“重新分析”会明确启动一次新任务，即使当前已有有效结果；运行中继续点击不会重复启动任务。重新生成的结果即使内容相同，也会记录新的生成时间。分析失败时可重试；最近的旧结果文件按留存数量保留，但不会作为新任务的成功结果展示。

## 配置

默认使用规则分析，不调用模型。规则输出仍包含证据、检查步骤、处理方向和复测要求。页面会标明规则分析与模型辅助分析的区别。

需要模型辅助时，在实际后端环境配置：

```dotenv
PRODUCTION_PLATFORM_TEST_FAILURE_ANALYSIS_MODEL_ENABLED=true
PRODUCTION_PLATFORM_TEST_FAILURE_ANALYSIS_MODEL_BASE_URL=http://127.0.0.1:11434
PRODUCTION_PLATFORM_TEST_FAILURE_ANALYSIS_MODEL=qwen3:8b
PRODUCTION_PLATFORM_TEST_FAILURE_ANALYSIS_MODEL_TIMEOUT_SECONDS=240
```

模型必须由后端所在机器的本地 Ollama 提供；本功能沿用原智能体的本机接口约束，显式禁用环境代理、全局 opener 与 HTTP 重定向，不读取其他功能的外部模型密钥。修改 `.env.example` 不会使配置生效，实际配置方法沿用工程现有 `.env` / 进程环境机制。

模型只能排序，并逐字选择该问题对应的规则解释和待核对检查项。它不能自行扩写故障结论、维修工序或数值。启用模型后若模型不可用或输出校验不通过，会显示失败供重试，不把未完成推理标为成功。

可选配置：

- `PRODUCTION_PLATFORM_TEST_FAILURE_ANALYSIS_DIR`：分析缓存目录，默认 `DATA_DIR/defect-search/test-failure-analysis`；与原始报告目录分开。
- `PRODUCTION_PLATFORM_TEST_FAILURE_ANALYSIS_PROTOCOL_SOURCE_PATH`：用于核对日志 SHA256 的可信协议源码文件。未设置或不匹配时，输出版本核对限制，仍保留该次报告判定和阈值。

- `PRODUCTION_PLATFORM_TEST_FAILURE_ANALYSIS_RULES_CONCURRENCY`：规则任务并发数，默认 `3`（范围 1–16）。
- `PRODUCTION_PLATFORM_TEST_FAILURE_ANALYSIS_MODEL_CONCURRENCY`：模型任务并发数，默认 `1`（范围 1–16）。
- `PRODUCTION_PLATFORM_TEST_FAILURE_ANALYSIS_RETAIN_RESULTS`：每份证据包保留的分析结果数量，默认 `3`（范围 1–100）。

并发限制通过文件锁在共享缓存目录的进程间生效；同一证据包的重复请求始终复用运行中的任务。各进程应使用相同并发配置。清理仅操作当前证据包缓存，持有对应锁后清理中断任务目录及超过留存数的结果；不会删除报告、索引历史或返修记录。

分析缓存可随平台业务数据备份。页面通过报告 ID 请求，不接受浏览器指定任意文件路径、模型地址或提示词。

## 证据版本与缓存更新

扫描会核对文件内容摘要；即使文件大小和修改时间没有改变，JSON 内容更新也会被识别。分析读取和快照生成时会再次核对当前内容与索引，并重新解析 JSON 的失败证据版本及运行 ID。旧索引在下一次扫描时自动补充内容摘要，此前仍会校验证据版本和运行 ID。索引尚未更新或读取期间文件变化时，任务显示证据已更新，需重新扫描、刷新详情后再生成，避免旧版详情搭配新版分析。

重新扫描后，已删除的 LOG 或 encoder CSV 会从当前附件列表移除；JSON 仍有效时可以重新生成分析。已有失败证据和人工返修确认继续保留，仅附件变化不会使人工确认失效。原始 JSON 缺失或尚未完整写入时，不使用历史证据冒充完整的当前证据包。

可信协议源码的内容也参与缓存校验：修改源码后，已有分析显示需要重新生成，无需重启后端；分析执行期间源码变化时，本次结果不会发布。任务状态在判定“上次分析已中断”前会重新读取，避免任务刚完成时误报失败。

## API

接口前缀：`/api/defect-search/test-failures`。

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/reports/{id}/analysis` | 读取分析状态和当前证据对应的结果；不触发分析 |
| POST | `/reports/{id}/analysis` | 按当前报告生成或复用方案；`force=true` 明确重新执行；后台任务返回 202，已完成缓存返回 200 |

POST 请求体为 `{ "report_revision": "当前详情返回的 revision", "force": false }`，`force` 可省略，默认为 `false`；只有用户显式点击“重新分析”才传 `true`，跳过已完成结果的复用。`force` 不绕过编辑权限、证据版本、附件校验和运行中任务去重。版本已变化时返回 409；页面提示刷新报告详情，避免将新版分析显示在旧版失败证据旁边。达到规则或模型的并发上限时返回 409 并提示稍后重试；不同证据包可在上限内并行处理。

返回状态为 `idle`、`running`、`complete`、`failed`、`unsupported` 或 `stale`。响应包括报告 ID、报告版本、生成时间、`rules_only` / `model` 模式、错误和结构化结果。旧证据的方案不会当作新报告的当前结果展示。

## 2026-10-30 完整性与性能优化

- 失败行、`failure_details`、失败测试的 `error` / `last_handled_exception` 分别参与分类，不因已有分析项而忽略其他来源。摘要与引用限长，但继续扫描所有类别并返回省略计数。
- 只有明确的证据匹配才归类为电流速度问题；`current_speed` 模式下未知异常仍显示证据不足。右侧参考阻断与明确 LEFT 异常保留原有区分。
- 状态查询复用最多 30 秒的已验证文件摘要，缓存键包含文件设备号、inode、大小、mtime、ctime、索引及配置。原地改写并恢复 mtime 仍会使缓存失效；生成快照和发布结果前始终完整读取校验。一次请求不再重复计算同一指纹。
- 完成缓存必须通过 schema、报告身份/版本、来源文件、输入哈希、结果摘要、证据引用和模型输出结构校验；非法或缺失结果显示失败并允许重新生成。
- 更新后旧分析因代码指纹变化显示需重新分析。历史原始判定、返修记录保持原样。

## 分析边界

### 右侧参考点水失败

支持 `right-reference-{volume}ul` 阶段及 `trace.events` 中的 `right_reference_failure` 事件。分析记录事件中的规格、RIGHT 安装位和 `handled`，并引用原始事件及阶段，兼容新文案 `DUT trials for this tip volume not run`。各规格快照和本文件夹内的主报告使用独立分析缓存，后补某份快照附件只使该份分析需要更新。不同文件夹的证据身份与缓存始终隔离，即使其 SN 或运行标识相同。

即时快照可能仍把已捕获异常放在 `trace.last_failure`。只有结构化证据能证明是当前同规格参考异常时，才作为已处理异常解释；显式 `runtime_error`、测试执行异常、后续 LEFT 动作及其他规格异常不会被旧事件消除。右侧参考失败意味着该规格的左侧测量可能未执行，占位值不能用来诊断左侧传感器。参考流程中明确的软件接口错误仍独立保留，不自动断言右侧硬件损坏。

共享识别规则位于 `reference.py`，其内容也参与分析代码缓存指纹。更新代码并重启后端后，旧分析需要重新生成；原始报告与返修确认不由分析改写。只有 LOG 时仍可查看和分类，完整智能分析需要对应 JSON 到齐。

目前完整支持协议 `schema_version=1` 的 JSON 证据包。页面原有 LOG 降级查看仍可用；仅有 LOG、未知 schema 或不完整 JSON 时，不据此生成完整智能体方案。

没有维修 SOP 时，输出检查、处理方向和复测要求；内部拆装、换件工序及装配参数交工程人员确认。右侧参考失败导致的左侧未测与实际左侧不合格分别处理；未执行检查的零值占位不能解释为实测零值；最近压力不能替代保护触发瞬间压力。

测试协议、正式 CSV 输出、原始附件、原 PASS/FAIL 以及已有人工返修确认均不由分析任务修改。
