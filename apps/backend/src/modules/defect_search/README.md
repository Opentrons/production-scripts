# 缺陷分析助手

## 按实际描述提供建议

检索后首屏显示“处理建议”，包括历史临时措施、采用记录数、适用型号/工站/代码和本地来源。明确对应的案例给出当前处理建议；单型号的相似案例或条件尚未确认的案例显示为“符合条件时参考”。多型号、并列措施和不同故障场景分别列出历史措施，支持选择型号或完整现象继续检索。

例如可输入 `Latch Fail`、`HS 琐臂回位测试 Latch Fail`、`Latch Fail 复测无效`、`60s漏液`。已明确报告复测失败时，系统保留缺陷历史并排除再次裸复测，继续查找尚未执行的历史措施。只有数值、位置或通道时先补充异常表现。

建议未解决或出现新情况时，点击“补充实际现象，继续分析”，回到搜索框补充当前表现、报错及已采取措施和结果后重新检索，也可交由工程根据实际问题分析。每次建议以最新提交的描述和筛选条件为依据。

案例内的“记录处理结果”用于可选留档，设备 SN 可选，首次保存生成独立记录组；当前页面可重新打开同一参考案例查阅，页面刷新后可从来源详情查阅已保存反馈。获取建议不要求先填写处理结果。留档接口返回结果说明，引导补充实际描述重新检索或提交工程分析。

## 本地数据

默认目录为 `apps/backend/data/defect-search/`，可通过 `PRODUCTION_PLATFORM_DATA_DIR` 更换上级数据目录。

- `knowledge.sqlite3`：原始案例、临时措施档案、来源证据、处理结果和导入记录。
- `backups/`：迁移、导入前以及手动创建的本地数据库备份。
- `model-cache/`：已部署的中文向量模型，运行时仅从本地加载。
- `embeddings.npz`：根据有效案例生成的向量索引，案例变更后自动重建。
- `seed.csv`：可选的本地初始化台账，不进入源码或 Python 安装包。

首次创建数据库时从本地 `seed.csv` 导入，也可通过 `PRODUCTION_PLATFORM_DEFECT_SEED_PATH` 指定其他 CSV 路径。没有初始化文件时建立空知识库，由管理员在页面中导入。此后以 SQLite 为准，替换 seed 不会覆盖现有数据。案例的 `local_id` 保持稳定，来源链接指向本地 `/api/defect-search/source/{id}`。

部署脚本保留服务器的 `data/` 目录，但不会同步本机台账。新服务器需要单独放置初始化文件，或启动后由管理员导入 CSV；已有数据库无需重新导入。实际台账包含设备和维修信息，应随业务数据备份与迁移。

## 临时措施

`defect_cases` 保留原始记录；仅有编号的空模板标记为 `is_active=0`。`temporary_action_profiles` 按型号、工站、缺陷代码和标准化描述分组，`temporary_action_evidence` 保存每条有效案例的临时措施原文。

普通查询复用按数据库及 WAL 文件版本缓存的快照，返回独立副本。案例改变后刷新派生档案和证据；缺失临时措施不会用原因或长期措施补齐。

措施字段的填报率与可推荐措施分开计算：原因陈述、仅有零件号、未处理和失败结果保留原文，但不直接推荐。`non_action_cases` 表示匹配案例中已填写但不足以构成可执行措施的记录数。

型号大小写及常见分隔符统一；G3、MINI 等硬件变体继续分别统计。措施合并会去掉历史主板 SN，保留零件号、版本、通道、方向和操作顺序；来源详情保留措施原文。

## 推荐规则

- 输入中的已知型号和缺陷代码作为筛选条件。型号按完整名称优先识别，支持 `Gripper MINI`、`P50M G3` 等分隔写法，MINI/G3/基础型号不混用。
- 序列号和零件号可与现象一起输入；处置关键词可单独填写。“漏液 复测”要求缺陷现象和历史处置同时符合，措施文字不参与现象匹配。
- 秒数按数值匹配，`60s`、`60 秒`、`60″` 等价，并与 `160秒` 区分。
- 缺陷状态中的 `Fail / Failed / Failure / NG / 失败` 统一识别；支持 `Fail Latch` 等不改变含义的词序变化。`widthFail / 宽度 NG`、`协议测试 NG / 协议失败` 等已确认写法统一参与统计。
- H1/H12、X/Z 轴、通道、数值和比较条件作为明确约束；小数点、负号、范围和故障时序保留。多个未单独绑定的数值参数保持原顺序，避免将 speed/current 的参数对调。独立绑定的秒数与通道仍可调整输入顺序。
- 明确匹配缺陷描述时直接检索；语义检索只对现象字段建立向量，避免措施文字影响缺陷判断。
- 推荐按匹配案例的型号分别统计，每型号展示前三项临时措施和本地来源。相似案例会标记为参考；泛词或只有型号时不汇总措施。
- 容量测试失败遵循“先复测”，该顺序为用户指定规则。
- 容量测试工站本身不能触发复测原则；黑屏等其他异常仍按实际现象检索。
- 采用次数和占比表示历史记录频次，不能视为修复成功率。
- 单例、多例和明确验证记录分别标示；未归类的不同现象不会合并生成首步更换建议。
- 每个型号独立选择建议依据；有完整归一描述与输入等价的记录时，优先使用这些记录。例如 `Latch Fail` 使用 HS 的完整同名记录；`Latch -Homung Fail` 等相关记录保留展示，不混入该建议的采用次数。没有完整匹配的未归类混杂记录继续要求核对现象；秒数查询保留原有时长和通道约束下的统计范围。
- 型号确认以全部检索结果为准；某型号的建议依据不足时，不会自动选用另一型号的措施。

## 当前处理建议

查询响应保留 `first_step` 字段，由 `guidance.py` 生成，页面展示“处理建议”。初始全库浏览不展示；提交缺陷查询或筛选后，按以下顺序选择：

1. 容量测试失败：遵循用户规则，先复测。
2. 信息过泛、缺少现象：先补充具体表现。
3. 无对应案例或未填写措施：补全信息并提交工程分析或确认临时措施。
4. 多个型号或并列措施：列出对应历史措施供选择；单型号相似案例、跨工站/代码或宽泛现象：明确适用条件后给出历史参考。
5. 明确同型号、同工站/代码的现象：参考唯一最高频的历史临时措施；最高频并列时先比较来源案例。

历史措施同时返回采用次数、匹配样本数和本地来源。当前建议作为历史参考；更改尚未提交的搜索条件、加载或请求失败时隐藏旧建议。时长写法等价时仍按原有规则匹配，历史案例额外限定的通道、位置或阶段应在适用条件中明确提示。

响应同时返回 `reason`、`products`、`stations`、`defect_codes`、`conditions`、`alternatives` 和兼容旧客户端的 `next_step`。后者仅给补充描述重新检索或工程分析的方向。确认提示明确说明需选择型号、工站、缺陷代码或补充故障阶段；型号候选按钮保留实际匹配到的型号，即使该型号暂时没有可用措施建议。`attempted_action` 保存本次输入明确报告失败的复测动作。

## 处理结果

案例内可“记录处理结果”，填写实际措施、复测结果、复发情况及备注供后续查阅。Schema v4 为 `defect_feedback` 增加 `repair_session_id` 和 `actual_serial_number`，升级前自动备份。记录组绑定登录用户、参考案例和首次保存的实际设备 SN；旧回填继续作为来源案例历史保留。回填独立保存，不修改台账，也不自动作为已验证历史依据。

来源详情和处理记录组均只显示当前登录用户保存的反馈，包括实际设备 SN、备注与检索词；管理员也不会通过此接口读取他人的反馈。

保存失败或复发结果后，提示补充实际现象、报错、已采取措施和结果，重新检索或提交工程分析。反馈接口仅返回结果说明，不根据来源案例的条件及剩余历史频次编排下一项换件。已执行措施需要在后续查询描述中明确提供。

## 维护

管理员可在页面底部“知识库维护”查看状态、预览 CSV、确认导入和手动备份；对应后端接口也强制校验管理员权限。保留原 CSV 英文列名，必需列为 `source/source_sheet/source_row/product/defect_description/containment_action`；来源行号必须为正整数，同一来源键不能重复。

导入按来源、工作表和原行号原位更新，保留本地 ID 和处理结果，未出现在导入文件中的旧记录保留。预览令牌绑定文件及现有数据版本；数据改变后需重新预览。正式导入先备份，原始数据与派生档案在同一事务中提交。页面显示数据版本、备份及最近导入记录。

本地详情通过现有认证客户端打开弹窗；检索条件保存在 URL，支持取消请求及超时提示，旧响应不能覆盖新搜索。
